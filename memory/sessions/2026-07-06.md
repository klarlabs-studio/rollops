## Session 2 — deep-review-and-harden → v0.20.0

Full crown-jewel security/correctness review of the whole daemon (6 parallel
read-only dimension agents), then remediation via 5 file-disjoint worktree
fix-agents + a release. **~30 findings: 3 CRITICAL, 12 HIGH, ~12 MED, ~10 LOW.**

### The 3 CRITICALs (all verified against source before fixing)
- **C1 — crashloop-on-arrival never rolled back.** An in-deploy health-gate
  failure marked the rollout `rolled-back` but left the broken version live;
  reconcile returned before `VerifyOrRollback` (the only path that re-applied
  prior), and next tick saw checksum-match = no drift → permanent. Compounded by
  a reconcile bug: `VerifyOrRollback` was passed `rl.Desired` (the NEW manifest)
  as `prior`, so even the post-deploy auto-rollback re-applied the broken version.
- **C2 — web console had NO RBAC.** Every mutating UI route ran as a hardcoded
  `admin` identity; the OIDC gate checked authentication only (no group/role), so
  any authenticated SSO user could rollback/approve/freeze prod, and all audit was
  mis-attributed to "admin". REST/gRPC/MCP were clean — UI was the outlier.
- **C3 — rollback never restored traffic weight or disabled the flag.** Traffic
  only ever shifted toward the canary; a failed canary at 100% kept serving 100%
  of prod traffic after "rollback".

### Fix PRs (all merged, CI green, full suite green on merged main)
- #38 supply-chain: digest-pin preservation (fail-closed, no immutable→mutable

- #39 plugin-host: env-scrub confinement (`ROLLOPS_PLUGIN_ALLOWED_ENV`,

## What Went Wrong / Gotchas
- **`isolation: worktree` gave each agent a *tokenops* worktree** (the CWD repo),
  not rollops. Every fix-agent adapted by making its own fresh rollops worktree
  off origin/main — isolated from each other + the main checkout. Worked, but the
  isolation was cosmetic; the gopls "not in workspace / undefined symbol"
  diagnostics were noise from those ad-hoc worktrees.
- **Breaking default:** #41 makes rollopsd refuse a non-loopback plaintext bind
  without `ROLLOPS_ALLOW_PLAINTEXT=1`. rollopsd binds `:8080` in-cluster → would
  fail to boot on upgrade. Mitigated by setting the env in the k8s manifest (TLS
  terminates at the ingress). Kept secure-by-default per operator's "best practice".

## BLOCKER — ghcr image push denied (release incomplete)

but the **image job failed**: `denied: permission_denied: write_package` for
`ghcr.io/klarlabs-studio/rollopsd:v0.20.0`. Root cause (pre-existing — v0.19.0's
image failed identically, so the cluster is still on the v0.18.0 image): **no
`CR_PAT` repo secret** AND the ghcr `rollopsd` package is `internal` + **not
linked to the repo** (`repository: None`), so the fallback `GITHUB_TOKEN` can't
push. FIX (org-admin): add a `write:packages` PAT as repo secret `CR_PAT`, OR link
the ghcr package to the repo with Write in "Manage Actions access". Then re-run
the failed image job: `gh run rerun 28809739025 --failed -R klarlabs-studio/rollops`.
Do NOT apply the v0.20.0 deploy pin until the image exists.

## Session 3 — v0.21.0 TLS/mTLS + release infra resolved

- **v0.21.0 shipped** (native TLS 1.3 + mTLS, PR #46): removed the
  `ROLLOPS_ALLOW_PLAINTEXT` env kill-switch entirely (operator flagged it as a
  security anti-pattern — an env flag that disables transport encryption). Now a
  non-loopback bind REQUIRES `ROLLOPS_TLS_CERT`/`_KEY`, no override; mTLS
  (`ROLLOPS_TLS_CLIENT_CA`) required on gRPC/REST/MCP, UI stays TLS+OIDC; cert
  hot-reload; new `internal/servertls`. GitHub release + binaries + image all live.
- **ghcr push blocker RESOLVED.** Operator granted the rollops repo Write in the
  ghcr package's "Manage Actions access" (there's no manual "Connect repository"
  UI for container packages — linking is via the OCI label). #45 added
  `org.opencontainers.image.source` to the Dockerfile; on the v0.21.0 push the
  package **auto-linked** to klarlabs-studio/rollops, so the `write_package`
  denial that killed v0.19.0's image (and initially v0.20.0's) can't recur.
- **mTLS CA-chain fix** (deploy-only, this PR): the v0.21.0 manifest issued the
  server cert straight from a self-signed ClusterIssuer, so the mounted `ca.crt`
  was the server's own leaf and NO client cert could verify → mTLS was
  non-functional. Fixed to a real chain (selfsigned → root CA cert → CA Issuer →
  server + client certs) + added `rollops-client-cert.example.yaml`. LESSON: a
  cert-manager SelfSigned issuer never produces a usable shared CA for mTLS;
  bootstrap a CA Certificate + CA Issuer.
